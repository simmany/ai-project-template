코딩·업무 에이전트에게 여러 단계에 걸친 긴 작업을 위임하고, 비서 에이전트가 진행 상황과 다음 할 일을 챙기게 하려면 사람이 해야 할 일이 있습니다. 목표와 역할을 정하고, 자료와 기준을 주고, 결과를 검토하는 일. 바로 ‘팀장의 기술’입니다.

이 세션의 중심은 폴더 기반의 컨텍스트 구조화입니다. 업무 자료·규칙·작업 기록을 폴더에 정리해 AI가 내 일을 이해하고 이어 가도록 준비하는 방법과, 서비스마다 자료와 지침을 전달하는 방식을 살펴봅니다. 이렇게 준비한 자료와 규칙이 여러 에이전트를 한 팀으로 꾸리는 ‘하네스’의 바탕이 되는 과정도 소개합니다. 아울러 위임한 일이 멈춰 있지 않도록, 비서 에이전트가 폴더의 작업 기록을 읽고 챙기는 흐름까지 다룹니다.

이 문서는 세션의 본론 ‘폴더 하나, 팀 하나, 비서 하나’를 내 컴퓨터에서 따라 해 보는 실습 가이드입니다. 템플릿 폴더에 자료와 기준을 넣어 업무 에이전트에게 맡기고, 하네스로 에이전트 팀을 꾸리고, 비서 에이전트가 진행 상황과 다음 할 일을 챙기게 만듭니다.

한 에이전트가 조사하고, 쓰고, 스스로 검토하면 놓치는 것이 생깁니다. 역할을 나누면 쓰는 쪽과 검토하는 쪽이 갈립니다. 카카오 황민호 수석이 만든 Harness v2(revfactory/harness)는 “하네스 구성해줘” 한 문장으로 도메인 설명을 에이전트 팀과 그 팀이 쓸 스킬로 바꿔 주는 Claude Code 플러그인입니다.

순서가 중요합니다. 1단계에서 준비한 폴더가 팀 구성의 재료가 됩니다. 그래서 폴더를 먼저 채우고 하네스를 부릅니다.

이번 REQ역할을 어떻게 나누고 어떤 순서로 일할까

파일workflow/2026-11-15_REQ-002 교육 제안서 완성.md
# Objective
신입 사원 AI 교육 제안서를 고객사에 보낼 수 있는 완성본으로 만든다.

# Context
- @input/교육요청서.md
- @output/ 의 가장 최신 제안서 초안

# Instruction
1. 요청서의 조건에 맞는 3일 과정의 구성 방식과 시간 배분을 조사해 근거로 정리해줘.
2. 조사 결과를 반영해 @output/ 에 제안서 완성본을 만들어줘.
3. 작성 기준과 요청서에 비추어 완성본을 검토하고, 고친 내용을 정리해줘.

# AI Response
(AI가 요청 번호별로 작성)

조사, 작성, 검토. 요청이 세 갈래라서 팀으로 나누기 좋습니다.

사람이 직접 쓴 요청 파일에는 첫 줄 표시가 없습니다. 표시가 없으면 사람이 쓴 요청입니다.

2-4하네스를 구성한다

에이전트에게 보내는 말
AGENTS.md를 먼저 읽고, input/과 rules/를 바탕으로 workflow/의 REQ-002에 맞는 하네스를 구성해줘.
팀원들도 AGENTS.md의 폴더 규칙을 따르게 해줘.
중간 산출물은 _workspace/drafts/REQ-002/ 아래에만 두고, _workspace/ 폴더와 그 안의 memory/는 옮기거나 지우지 마.
CLAUDE.md의 첫 줄 @AGENTS.md는 그대로 두고, 하네스 기록은 그 아래에 추가해줘.
팀원별 역할과 작업 순서를 먼저 제안하고, 내가 확인한 뒤 작업을 시작해줘.

첫 줄, 둘째 줄, 마지막 줄은 템플릿 폴더가 권하는 호출 문장입니다. 가운데 두 줄은 이 폴더를 지키려고 더했습니다.

  • _workspace/를 지킨다. 하네스가 만드는 팀은 중간 산출물을 _workspace/ 바로 아래에 두고, 새 입력으로 다시 실행할 때 기존 _workspace/를 다른 이름으로 옮기도록 만들어질 수 있습니다. 이 폴더는 작업노트가 _workspace/memory/에 있습니다. 옮겨지면 비서 에이전트가 읽을 노트가 사라집니다.
  • @AGENTS.md를 지킨다. 하네스는 CLAUDE.md에 호출 조건과 변경 이력을 기록합니다. 그때 첫 줄 @AGENTS.md가 남아 있어야 Claude Code가 계속 AGENTS.md를 읽습니다.

2-5제안을 확인하고 승인한다

하네스는 폴더를 읽고 팀 구성을 제안합니다. 승인하기 전에 네 가지를 봅니다.

  • 대표 에이전트가 REQ·AI Response 기록과 status.md 갱신을 맡는가.
  • 검토 역할이 작성 역할과 따로 있는가.

2B

다른 길: 만들어 둔 팀을 골라 쓴다

20분 안팎

끝나면 AI 워크스페이스 표준의 팀 하나가 내 프로젝트가 되고, 그 안에 템플릿 폴더가 얹힙니다. 2단계와 둘 가운데 하나만 해도 됩니다.

2단계의 Harness v2는 카카오 황민호 수석이 만든 메타 하네스입니다. 목표와 작업에 맞는 팀을 그 자리에서 짓습니다. 팀을 꾸리는 길이 하나 더 있습니다. 박성혁 대표의 AI 워크스페이스 표준은 미리 잘 만들어 둔 팀 가운데 내 일과 가장 가까운 팀을 골라 고쳐 쓰는 방식입니다. 이 미리 만들어 둔 팀을 변형(variant)이라고 부릅니다.

Harness v2AI 워크스페이스 표준
방식목표와 작업에 맞춰 팀을 그 자리에서 짓는다만들어 둔 팀(변형) 가운데 가장 가까운 것을 골라 고쳐 쓴다
시작하는 말“하네스 구성해줘”new-project --variant co-work
팀이 사는 곳내 폴더 안의 .claude/변형에서 만든 프로젝트 폴더 전체
템플릿 폴더와의 관계내 폴더 안에 팀이 생긴다팀의 폴더 안에 내 폴더를 얹는다
잘 맞는 때일마다 필요한 팀이 다를 때조직이 같은 표준으로 여러 팀을 운영할 때

왜 변형인가

조직이 에이전트 팀을 함께 쓰는 방법은 둘입니다. 하나는 공용 팀 하나를 두고 요청을 티켓으로 받는 방식입니다. 설치할 것이 없고 통제가 쉽지만, 요청마다 맥락이 끊기고 조직이 커질수록 창구 하나가 병목이 됩니다. 다른 하나가 변형 방식입니다. 함께 쓰는 것은 에이전트가 아니라 표준과 팀 템플릿이고, 팀마다 그것을 복제해 자기 프로젝트로 갖습니다. 맥락이 그 프로젝트의 저장소와 기록에 쌓이고 서로의 대기열을 타지 않습니다. 대신 처음 꾸리는 비용이 들고, 표준이 없으면 팀마다 달라집니다.

AI 워크스페이스 표준은 뒤쪽을 고르고 그 약점을 구조로 막습니다. 맨 위에 공통 규칙(CONSTITUTION.md)을 두고, 워크스페이스에서 공통 템플릿, 변형, 프로젝트로 내려가는 네 계층을 둡니다. 핸드북은 두 방식을 가르는 기준을 일이 반복되느냐가 아니라 맥락이 얼마나 깊이 필요하냐로 봅니다. 티켓을 없앤 것도 아닙니다. 다른 팀에 일을 넘기는 좁은 통로로 남겨 두었습니다.

~/git/                               워크스페이스 루트: 표준 저장소
└── Projects/edu-proposal/           co-work 변형으로 만든 내 프로젝트
    ├── AGENTS.md · CLAUDE.md        팀의 명부와 행동 지침 (그대로 둔다)
    ├── PERSONAL-AGENT.md            ← 템플릿에서 얹는다 (3단계에서 쓴다)
    ├── agents/ · skills/            PM과 전문 에이전트, 스킬
    ├── docs/co-work.context.md      프로젝트 설정 ← 규칙 한 줄을 더한다
    ├── deliverables/ · memory/      팀의 작업물과 세션 기록
    ├── rules/                       ← 템플릿에서 얹는다 (+ folder-rules.md)
    ├── workflow/                    ← 템플릿에서 얹는다
    ├── input/                       ← 템플릿에서 얹는다
    ├── _workspace/memory/status.md  ← 템플릿에서 얹는다
    └── output/                      ← 템플릿에서 얹는다

아래 연동 방법은 표준이 정한 절차가 아닙니다. 저장소 문서와 핸드북을 읽고 짠 구성이니, 처음에는 연습용 프로젝트에서 돌려 보세요.

터미널Bun 설치 · Windows

~/git을 이미 쓰고 있다면 비어 있는 다른 폴더로 받고, 아래 명령의 ~/git을 그 폴더로 바꿉니다. 다른 프로젝트 폴더 안에는 넣지 않습니다.

2B-3템플릿의 다섯 폴더를 얹는다

이름이 겹치는 것은 AGENTS.md와 CLAUDE.md뿐입니다. 이 둘은 팀의 것을 그대로 두고, 템플릿의 다섯 폴더와 PERSONAL-AGENT.md를 가져옵니다. 템플릿의 AGENTS.md는 rules/folder-rules.md라는 이름으로 넣습니다.

첫 줄의 경로는 템플릿으로 일하던 폴더입니다. 3단계의 입력 칸에 적어 두었다면 채워져 있습니다.

터미널macOS · Linux
T="/Users/내이름/Projects/교육제안서"
cd ~/git/Projects/edu-proposal
cp -R "$T/rules" "$T/workflow" "$T/input" "$T/_workspace" "$T/output" .
cp "$T/AGENTS.md" rules/folder-rules.md
cp "$T/PERSONAL-AGENT.md" .

Finder나 탐색기에서 다섯 폴더와 PERSONAL-AGENT.md를 끌어다 놓고, AGENTS.md를 복사해 rules 폴더 안에서 이름을 바꿔도 됩니다. 1단계에서 쓰던 폴더에서 가져오면 요청 기록과 작업노트가 함께 따라옵니다. 숨김 폴더 .claude/는 가져오지 않습니다.

2B-4연결 규칙 한 줄을 더한다

프로젝트의 docs/co-work.context.md를 열어 ## Domain Rules 목록 맨 아래에 다음 번호로 붙입니다. 이 파일은 이 표준이 영어로 쓰도록 검사하는 문서라서 규칙도 영어로 적습니다.

파일docs/co-work.context.md 의 Domain Rules 에 추가
7. **Project folder contract [ai-project-template]**: This project also carries the folders `rules/`, `workflow/`, `input/`, `_workspace/`, and `output/`. PM reads `rules/folder-rules.md` at session start and follows it. PM records each request and its result in the `workflow/` REQ file. PM saves the approved final deliverable to `output/` with a version suffix. PM updates `_workspace/memory/status.md` when a request ends. Team working files stay in `deliverables/`; if `rules/folder-rules.md` names a different draft location, this rule wins.

뜻은 이렇습니다. PM이 세션을 시작할 때 폴더 규칙을 읽는다. 요청과 결과를 workflow/의 REQ 파일에 기록한다. 승인된 최종본을 output/에 버전을 붙여 저장한다. 요청이 끝나면 status.md를 갱신한다. 팀이 일하는 동안의 초안과 조사는 변형의 방식대로 deliverables/에 둔다. 팀이 안에서 일하는 방식은 건드리지 않고, 사람과 비서가 만나는 자리만 템플릿 폴더로 맞추는 것입니다.

비서 에이전트가 챙기게 한다

20분 안팎

끝나면 정해 둔 시각에 비서 에이전트가 폴더를 읽고, 진행 상황과 다음 할 일을 먼저 알려 줍니다.

스케줄로 깨어난 비서 에이전트는 지난 대화를 들고 있지 않은 경우가 많습니다. Hermes의 예약 작업은 이전 실행의 대화 없이 매번 새로 시작합니다. 그래서 일의 상태는 폴더에 적어 두고, 비서는 깨어날 때마다 폴더를 읽게 합니다. 비서의 기억에는 약속과 내 사정만 남깁니다. 약속은 이름, 맡긴 폴더, 그 폴더에서 따를 파일입니다. 내 사정은 언제 확인하기로 했는지, 내가 어떤 보고를 좋아하는지입니다.

이 단계의 연결 방법은 제품이 정해 둔 절차가 아닙니다. 각 제품의 문서에서 확인한 사실을 바탕으로 짠 구성입니다. 약속 글과 폴더의 규칙은 Claude에 비서 에이전트의 이름과 기억을 주어 시험했습니다. Hermes나 dot이 쓰는 모델이 같은 글을 같게 읽는지는 확인하지 못했습니다. 그래서 읽기 권한으로 시작합니다.

3-1약속을 말하고 이름을 등록한다

폴더에 글을 적어 두는 것만으로는 비서 에이전트를 묶을 수 없습니다. 다른 곳에서 시작해 이 폴더를 찾아온 에이전트에게 폴더의 파일은 지침이 아니라 읽은 내용입니다. 그래서 약속을 두 곳에 둡니다. 비서 에이전트에게는 내가 직접 말해 두고, 폴더에는 그 비서의 이름을 등록합니다. 두 곳의 이름이 같을 때만 비서 에이전트가 이 파일의 규칙을 따릅니다.

  1. 이름을 정합니다. 비서 에이전트가 이미 쓰는 이름(처음 설정할 때 지어 준 별명)이 있으면 그 이름을 씁니다. 제품 이름(Hermes, dot, Claude)뿐이면 여기서 지어 줍니다. 이 가이드는 ‘모아’로 적습니다.
  2. 폴더에 등록합니다. PERSONAL-AGENT.md를 열어 ‘등록’의 두 줄을 아래처럼 채웁니다. 권한은 ‘읽기’ 그대로 둡니다.

- 권한(읽기 또는 맡기기): 읽기
