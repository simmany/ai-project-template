# 4단계. 지켜야 할 규칙을 rules 폴더에 두기

`rules/`에는 매번 말하지 않아도 에이전트가 지켜야 할 기준을 둡니다. 에이전트는 작업을 시작할 때마다 이 폴더 바로 아래의 파일을 먼저 읽습니다. 규칙 파일은 `rules/` 바로 아래에 둡니다. 그 안에 만든 폴더(예: `coding/`)의 파일은 규칙 파일이 가리킬 때만 읽습니다.

폴더에 미리 들어 있는 `coding.md`와 `coding/` 폴더는 코딩 기본 기준과 그 예제입니다. 6단계에서 쓰니 지금은 그대로 둡니다.

규칙은 직접 써서 넣어도 되지만, 처음에는 에이전트에게 초안을 만들게 하는 편이 쉽습니다. 규칙을 만들어 달라고 하는 요청을 메타 프롬프트라고 부릅니다. 보고서, 기획서, 제안서, 사업계획서 같은 문서에는 세 가지를 만들어 둡니다. 결과물의 품질을 고르게 잡아 주는 세 가지 장치입니다.

- 목차: 문서의 뼈대
- 작가 페르소나: 이 문서를 쓰는 사람이 어떤 전문가이고 어떤 말투로 쓰는지 적은 글
- 독자 페르소나: 이 문서를 읽고 결정할 사람이 누구이고 무엇을 궁금해하는지 적은 글

## 메타 프롬프트의 짜임

아래 '따라 하기'의 요청은 모두 같은 짜임입니다.

- 첫 문장: 무엇을 읽고 무엇을 만들어 어디에 저장할지 적습니다. "앞으로 이 프로젝트에서 지킬 기준으로 쓸 거니까 rules/...로 저장해줘"를 붙이면 에이전트가 어디에 둘지 되묻지 않습니다.
- 대괄호로 묶은 조건: 분량과 깊이, 꼭 들어갈 내용, 만들어질 기준 파일의 모양을 적습니다. `[제약사항]`, `[반드시 포함할 내용]`, `[출력 형식]`처럼 이름을 붙여 나눕니다.

내 업무에 쓸 때는 대괄호 아래의 줄을 내 문서에 맞게 고칩니다.

## 따라 하기

실습에서는 아래 요청 넷을 차례로 보내면 됩니다. 하나를 보내고, 만들어진 파일을 읽어 본 뒤 다음으로 넘어갑니다. 업무 에이전트에서 새 대화로 시작한다면 첫 요청의 맨 앞에 'AGENTS.md를 먼저 읽고,'를 붙입니다.

먼저 목차입니다.

```
input/교육요청서.md를 읽고 이 제안서의 목차를 만들어줘. 앞으로 이 프로젝트에서 지킬 기준으로 쓸 거니까 rules/목차.md로 저장해줘.

[제약사항]
- 대목차 5~7개, 대목차마다 중목차 2~4개
- A4 5~6쪽 분량
- 인재개발팀장이 읽고 결정하는 문서

[반드시 포함할 내용]
- 교육 요청서의 '꼭 들어갈 내용'
- 3일 일정표
- 예산
- 기대 효과

[출력 형식]
- 1. → 1.1 형식의 번호
- 대목차마다 쪽수 배분을 함께 적기
```

다음은 작가 페르소나입니다.

```
rules/목차.md의 목차로 제안서를 쓸 작가 페르소나를 만들어줘. 앞으로 이 프로젝트에서 지킬 기준으로 쓸 거니까 rules/작가 페르소나.md로 저장해줘.

[작가 페르소나 요구사항]
- 전문성: 기업 교육 기획자 (경력 10년 이상)
- 특화 분야: 비개발 직군 대상 AI 실무 교육
- 글의 어조: 실용적이고 명료하게, 결정하는 사람을 설득하는 어조
- 관점: 현업의 시간과 예산, 보안 제약을 아는 실무 중심
- 표현 방식: 전문 용어를 줄이고 숫자와 사례로 말하기

[출력 형식]
- 전문 분야와 관점
- 글쓰기 스타일 가이드 (어조, 문장, 용어)
- 쓰지 않는 표현
```

그다음은 독자 페르소나입니다.

```
이 제안서를 읽고 결정할 사람의 독자 페르소나를 만들어줘. 앞으로 이 프로젝트에서 지킬 기준으로 쓸 거니까 rules/독자 페르소나.md로 저장해줘.

[독자 정보]
- 1차 독자: 가람물류 인재개발팀장 (교육을 결정하는 사람)
  - 관심사: 3일 뒤에 신입 사원이 무엇을 할 수 있게 되는지, 예산 안에서 되는지
  - 걱정: 보안 사고, 현업과 동떨어진 교육
  - 읽는 시간: 5분 안에 핵심을 파악하고 싶어 함
- 2차 독자: 교육을 운영할 인재개발팀 담당자
  - 관심사: 일정, 준비물, 역할 분담

[표현 난이도]
- 전문 용어에는 쉬운 설명을 함께 적기
- 핵심은 표로 요약하기
- 첫 쪽에 한 장 요약 두기
```

세 파일이 생기면 규칙에 맞춰 다시 만들게 합니다.

```
새로 정한 rules/의 기준에 맞춰 제안서를 다시 만들어줘.
```

## 확인하기

- `rules/`에 `목차.md`, `작가 페르소나.md`, `독자 페르소나.md`가 생겼습니다.
- `output/`에 새 버전이 생겼고, 목차가 `rules/목차.md`와 같습니다.
- `workflow/`의 업무요청서에 방금 보낸 요청 넷이 적혔습니다. 처리 결과에는 있는데 요청 사항에 빠진 요청이 있으면 [막혔을 때](troubleshooting.md)의 '요청과 기록'을 봅니다.

`rules/`의 파일은 꼭 읽어 보고 고칩니다. 마음에 들지 않는 곳은 에이전트에게 고쳐 달라고 하거나 직접 고칩니다. 규칙은 에이전트가 쓴 초안이 아니라 내가 정한 기준이어야 합니다.

- 목차는 한 번에 다 만들지 않아도 됩니다. 대목차와 중목차까지만 먼저 잡고, "3장만 더 나눠줘"처럼 좁혀 가면 품질이 올라갑니다.
- 작가 페르소나와 독자 페르소나는 함께 둡니다. 누가 쓰고 누가 읽는지가 함께 정해져야 글의 방향이 또렷해집니다.
- 작가 페르소나에 가상 인물의 이름이나 이력은 넣지 않았습니다. 기준 파일에 필요한 것은 인물 소개가 아니라 글쓰기 지침이기 때문입니다.
- 조건에는 `input/`에 자료가 있는 것만 적습니다. 자료에 없는 통계나 현황을 꼭 넣으라고 하면 에이전트가 가정으로 채웁니다.

## 다른 업무라면

세 가지는 '결과물의 틀', '일하는 사람', '받는 사람'을 정해 두는 것입니다. 다른 업무에도 같은 자리에 맞는 규칙이 있습니다. 내 업무에 쓸 때 가까운 줄을 봅니다.

| 업무 | 결과물의 틀(목차에 해당) | 일하는 사람(작가 페르소나에 해당) | 받는 사람(독자 페르소나에 해당) |
| --- | --- | --- | --- |
| 보고서, 기획서, 제안서, 사업계획서 | 목차와 쪽수 배분 | 작가 페르소나 | 독자 페르소나 |
| 견적서, 안내문 | 양식(항목, 금액, 유효 기간) | 우리 가게의 말투와 약속해도 되는 범위 | 손님 |
| 데이터 분석 | 분석 보고 양식(질문, 쓴 데이터, 결과, 한계) | 분석가의 원칙(추정과 사실을 구분하고 출처를 적는다) | 보고받는 사람(결론을 먼저 원하는 임원) |
| 고객 문의 답변 | 답변 양식(인사, 답, 다음에 할 일) | 상담 담당자의 말투와 약속해도 되는 범위 | 고객 유형(처음 쓰는 고객, 불만이 있는 고객) |
| 회의록, 주간 보고 | 회의록 양식(결정한 것, 할 일, 담당, 기한) | 기록하는 사람의 원칙(해석하지 않고 결정만 적는다) | 읽는 사람(회의에 오지 못한 팀장) |
| 번역 | 용어집과 표기 기준 | 번역가의 문체 | 읽는 사람(현지 고객) |

보내는 말의 짜임은 같습니다. 견적서라면 "우리 가게의 견적서 양식을 만들어줘. 앞으로 이 프로젝트에서 지킬 기준으로 쓸 거니까 rules/견적서 양식.md로 저장해줘."라고 보내고, 그 아래에 대괄호로 조건을 붙입니다.

## 왜 규칙을 따로 두나요

- 요청마다 "합니다 체로 써줘", "3쪽으로 써줘"를 되풀이하지 않아도 됩니다.
- 규칙은 한 번 정하면 그 뒤의 모든 요청에 적용됩니다. 대화가 바뀌어도, 에이전트가 바뀌어도 같습니다.
- 요청이 규칙과 어긋나면 에이전트가 어긋난다고 알리고 어느 쪽을 따를지 묻습니다.
