# 코딩 기본 기준 (Coding Baseline)

사용자가 따로 정한 방법 없이 코딩을 시작할 때 쓰는 **기본값**이다.
이 파일은 세 가지를 정한다: **어디에 둘지, 어떤 기술을 언제 쓸지, 언제 사용자에게 물을지.**
실제로 실행되는 예제와 앱 폴더 구조는 `rules/coding-skeleton.md`에 있다.

## 1. 사용자가 정한 방법이 먼저다

- 사용자가 방법을 정했다면 **그 방법을 적용하라고 한 작업에만** 그 방법을 따르고, 나머지 작업은 이 기본값으로 한다. 기준은 지시가 대화·REQ 파일·스킬·설계 문서 중 어디에 적혔는지가 아니라, 어떤 작업에 적용하라고 했는지다.
  - "HWPX 생성은 이 스킬로 해" → 문서 생성 방식만 스킬을 따른다. 수집기 위치나 대시보드 기술은 이 파일대로 한다.
  - "이 프로젝트는 첨부한 설계서 구조로 구현해" → 프로젝트 전체를 설계서대로 한다.
- 기존 코드를 고칠 때는 그 코드의 스택과 실행 방식을 따른다.
- 다른 기술을 쓰게 되면 `coding-skeleton.md`에서 그 기술의 절(가상환경, 포트 등)은 보지 않는다. 2절 위치와 5절 공통 규칙은 그대로 지킨다.
- 어느 작업에 적용할지 애매하면 작업 전에 묻는다.
- `처리 결과`에 무엇을 기준으로 삼았는지 적는다. (예: "기본 기준 `rules/coding.md`로 진행, HWPX 생성은 ○○ 스킬")

## 2. 어디에 둘지 (항상 지킨다)

| 무엇 | 어디 |
|---|---|
| 반복해서 쓰고 고치는 코드 (HTML 도구, 스크립트, 앱) | `codebase/<앱이름>/` (`codebase/`가 없으면 만든다) |
| 특정 작업의 결과를 전달하는 파일 (CSV, 문서, HTML 보고서) | `output/` |
| 시험 삼아 짠 코드, 중간 산출물 | `_workspace/` |
| 사용자가 준 원본 자료 | `input/` (읽기만 한다) |

- 새 데이터를 넣거나 연결해 반복 사용하는 HTML 도구는 `codebase/<앱이름>/`에 둔다. 특정 작업의 결과를 전달하는 HTML 보고서는 `output/`에 둔다. 도구 자체가 납품 대상이면 전달본을 `output/`에 만든다.
- 앱이 쓰는 SQLite 파일은 `codebase/<앱이름>/db/`에 둔다. 사용자가 DB 파일 자체를 달라고 할 때만 전달용 사본을 `output/`에 만든다.
- 앱 폴더 안의 구조와 이름은 `coding-skeleton.md` 1절을 따른다.

## 3. 어떤 기술을 언제 쓸지

기본 스택: 화면은 HTML·CSS·JavaScript(vanilla, 빌드 없음), 처리는 Python, 서버는 Flask, 저장은 SQLite.
쓰지 않는다: React·Vue 등 프레임워크, TypeScript, npm 빌드 도구, ORM, Docker.

가장 단순한 것에서 시작하고, 아래 신호가 있을 때만 하나씩 더한다.

| 신호 | 쓰는 것 |
|---|---|
| (기본) 사용자가 고른 파일을 보고·거르고·내려받는다 | HTML 한 장 |
| 파일을 넣으면 파일이 나온다 (수집·변환·정리), 정해진 때 돌린다 | Python 스크립트 |
| 데이터를 쌓아 두고 다시 조회·수정한다 | SQLite (스크립트에서도 쓸 수 있다) |
| 화면의 버튼으로 Python 함수를 실행한다 | Flask |
| 브라우저에서 시작한 요청에 공용 비밀 키가 필요하다 | Flask (키를 가진 서버가 대신 호출) |
| 여러 사람이 같은 데이터를 고치고, 그 변경이 다음 사람 화면에도 보여야 한다 | Flask + SQLite |

- 서버 없이 되는 일: 각자 자기 파일을 편집하는 일, 여러 사람이 같은 화면을 보기만 하는 일, 스크립트가 `.env`의 비밀 키를 쓰는 일.
- 기존 업무 API나 서비스가 이미 그 역할을 하면 새 서버를 만들지 않고 그것을 쓴다.
- 스크립트는 처리 함수와 실행부를 나눠, 나중에 Flask가 그 함수를 그대로 가져다 쓰게 한다.
- Flask 화면은 기본 방식을 하나 정한다. 대시보드형은 JSON + JS, 관리 화면형은 Jinja2 템플릿. 부분 갱신이 필요한 곳에만 다른 방식을 쓰고, 같은 목록을 두 방식으로 그리지 않는다. 기본 방식은 앱 README 첫 줄에 적는다.
- 라이브러리는 필요하면 추가하고, 그 이유를 `처리 결과`에 적는다.

## 4. 언제 묻는지

이 파일이 허용한 기본값은 묻지 않고 바로 쓴다. 새 앱에 SQLite나 Flask를 처음 쓰는 것도 여기에 들어간다.
사용자의 설치·운영 조건이 달라질 때만 작업 전에 묻는다.

- 새 런타임이나 프로그램을 설치해야 한다 (Node.js, Docker 등)
- 이미 쓰던 방식을 바꾼다 (SQLite → PostgreSQL, 로컬 실행 → 외부 서비스, 화면 방식 변경)
- 내 컴퓨터 밖으로 공개·배포한다
- 3절에서 "쓰지 않는다"고 한 것이 필요하다
- 1절의 적용 범위가 애매하다

## 5. 항상 지킬 것 (어떤 방법을 따르든)

- 비밀값(API 키·비밀번호)은 `.env`에 두고 코드와 화면에 직접 쓰지 않는다. `.env`는 git에 올리지 않는다.
- SQL 값은 문자열로 이어 붙이지 않고, 드라이버가 제공하는 매개변수 바인딩으로 넘긴다.
- 사용자 입력이나 외부 데이터를 HTML 문자열에 이어 붙여 화면에 넣지 않는다.
- 미리보기·개발 서버는 내 컴퓨터(127.0.0.1)에만 열고, 공개할 파일이 있는 폴더만 제공한다.
- 입력이 이상해도 조용히 넘어가지 않는다. 결과가 0건이면 빈 결과를 새로 써서 이전 결과가 남지 않게 하고, 필수 항목이 없으면 오류를 알린다.
- 사용자가 쓰는 방식 그대로 실행해서 확인한다. HTML은 그 파일만으로 열어서 샘플 입력부터 내려받기까지, 서버는 실제 요청과 응답, 저장 기능은 재시작 후에도 데이터가 남는지.
- 앱 README에 실행 명령과 접속 주소를 적는다. 복사해 붙이면 바로 실행되게.
